O problema

Por que este backend existe.

Em ambientes de projeto de software, a composição de equipes costuma ser feita manualmente, com base na percepção individual do gestor e na disponibilidade imediata das pessoas. O resultado são times desnivelados — falta de competências essenciais, sobreposição de funções, sobrecarga dos profissionais mais experientes.

O sistema ataca isso em duas frentes que se complementam. Um motor preditivo calcula, para cada desenvolvedor, um escore de afinidade com o projeto. Um modelo de linguagem traduz esse número em uma justificativa legível, porque um escore sem explicação não sustenta uma decisão de alocação.

Este backend é a peça que amarra as duas. Ele não calcula o escore nem redige o texto: ele guarda o domínio, monta o que cada serviço precisa receber, aplica as regras de composição da equipe e devolve um resultado coerente.

O que o sistema precisa responder

  • Dado um projeto com papéis, stack e criticidade definidos, quem deve compor a equipe?
  • A equipe sugerida cobre todos os papéis e tecnologias exigidos?
  • O time está nivelado, ou é só um bloco de júniores em um projeto crítico?
  • Quando dois projetos disputam a mesma pessoa, quem fica com ela?
  • Por quê — em português, não em número.

Arquitetura

Quatro peças, dois ecossistemas, um orquestrador.

A arquitetura é de microsserviços por uma razão concreta: o motor de predição vive no ecossistema Python, onde estão as bibliotecas de aprendizado de máquina, enquanto a lógica de negócio e a persistência vivem no ecossistema Java. Em vez de forçar os dois no mesmo processo, cada um roda onde é forte e conversam por HTTP.

As duas vias de entrada

O trabalho prevê uma abordagem híbrida, e os dois caminhos convergem para a mesma pipeline de recomendação:

  • Fluxo estruturado — o gestor preenche formulários; o React envia JSON; o backend processa.
  • Fluxo conversacional — o gestor descreve a necessidade em português; o Gemini converte o texto em parâmetros de busca; a partir daí o caminho é idêntico.

É por isso que a entidade Recomendacao guarda um campo origem: as duas vias produzem o mesmo tipo de resultado, mas saber por qual delas o gestor chegou é dado de pesquisa deste trabalho.

Sobre o Spring Boot 3 e não 4. O Spring Initializr já não gera projetos 3.x, e o padrão hoje é a linha 4. Mesmo assim o projeto ficou no 3.5.16 por dois motivos: é a versão declarada no texto do TFG, e o Spring AI 1.1.x — que fornece a integração com o Gemini — tem como alvo o Boot 3.5. Sobre o acesso ao Gemini

O Spring AI oferece dois caminhos para os modelos do Google. O escolhido é spring-ai-starter-model-google-genai, que fala com a API do Gemini via chave de API — sem exigir conta na Google Cloud. A alternativa, vertex-ai-gemini, roteia pela Vertex AI e demanda projeto configurado no GCP, o que não se justifica em um protótipo acadêmico.

O caminho de uma requisição

  1. O controller recebe o JSON, que o Spring desserializa em um record de request. O @Valid reprova o que estiver fora das regras antes de qualquer código de negócio rodar.
  2. O controller chama o service e não faz mais nada — sem try/catch, sem consulta ao banco, sem lógica.
  3. O service abre a transação, usa os repositórios para carregar e gravar entidades, e aplica as regras.
  4. O mapper converte a entidade em um record de response.
  5. O controller devolve o record. A entidade JPA nunca chega ao JSON.

As quatro regras que sustentam isso

RegraO que ela evita
Entidade nunca vira JSON Vazar estrutura interna do banco na API e quebrar o React a cada refatoração
@Transactional só no service Transações abertas durante a serialização, prendendo conexão do pool
open-in-view: false Consultas disparadas silenciosamente na hora de gerar o JSON
Um repositório por agregado Alterar uma associativa por fora e deixar o objeto pai inconsistente

A terceira merece uma nota: com open-in-view ligado — que é o padrão do Spring Boot — a sessão do Hibernate fica aberta até a resposta ser escrita, e coleções preguiçosas são carregadas durante a serialização, uma consulta por item. Desligando, o carregamento passa a ser explícito no service, com JOIN FETCH.

A separação entre 400 e 422 é deliberada. Pedir uma equipe de -3 pessoas é um erro de formato: 400. Pedir uma equipe de 8 pessoas quando existem 3 desenvolvedores disponíveis é uma requisição bem formada que o domínio recusa: 422. E o 503 existe para que a queda de um serviço de apoio não derrube o backend inteiro.

As regras que o cadastro de projeto impõe

Todas existem para impedir que uma especificação incoerente contamine as métricas calculadas na composição da equipe.

RegraRespostaPor quê
Vagas por papel não excedem o tamanho da equipe 422 Somar mais tornaria a cobertura de papéis matematicamente inatingível
Somar menos é permitido 201 São posições sem papel fixo, preenchidas por quem tiver melhor escore
Cada papel declarado uma única vez 422 Duas quantidades para o mesmo papel são ambíguas
Término não anterior ao início 422 Período invertido quebra o cálculo de janela de alocação
Tecnologia exigida existe e está ativa 404 · 422 Requisito órfão inviabiliza a cobertura de tecnologias

O campo vagasSemPapelFixo devolvido pela API é a diferença entre o tamanho da equipe e as vagas distribuídas. Maior que zero significa que parte do time fica em aberto: essas posições são preenchidas pelos maiores escores, de qualquer papel.

Três decisões que aparecem no contrato

A normalização acontece no DTO, não no service. O Jackson constrói o record e só então o Bean Validation examina os campos. Aparar e converter para minúsculas dentro do compact constructor faz com que um e-mail colado com espaço em volta seja aceito — se a limpeza ficasse no service, o @Email já teria reprovado com 400.

A listagem não traz as competências. Carregá-las para cada linha da página dispararia uma consulta por desenvolvedor. Quem precisa da lista completa busca o perfil pelo identificador.

Duplicata é recusada, não resolvida em silêncio. Informar a mesma habilidade duas vezes, com proficiências diferentes, devolve 422 em vez de o backend escolher uma delas. Qualquer escolha automática gravaria algo diferente do que o cliente pretendia. Vale para desenvolvedores e para projetos.

O PUT substitui as competências, não acrescenta. É a semântica que o formulário do frontend espera: o que está na tela é exatamente o que fica gravado. Para mexer apenas nas horas existe o PATCH, que não corre o risco de apagar a lista sem querer.

Carga inicial do catálogo. Controlada pela propriedade app.seed.catalogo, ligada nos perfis dev e local. É idempotente: nada acontece se o catálogo já tiver registros. Traz as 30 tecnologias da pesquisa e 8 competências comportamentais. Como a aderência técnica é calculada no backend, qualquer tecnologia do catálogo conta para o escore, inclusive as cadastradas depois.

Alocacao

O compromisso confirmado pelo gestor. Só ela consome horas.

Por que Alocacao e RecomendacaoMembro são coisas diferentes. RecomendacaoMembro é uma sugestão do motor; Alocacao é um compromisso aceito. Sem essa separação, o cenário de avaliação “múltiplos projetos disputando os mesmos desenvolvedores” não teria como ser resolvido: não haveria como saber quantas horas de cada pessoa já estão de fato comprometidas.

Por que o ranking inteiro é gravado

Guardar só os selecionados economizaria linhas e custaria duas coisas. O gestor perderia a informação de quem ficou de fora e por qual margem — que é exatamente o que ele precisa para contestar a sugestão. E o modelo de linguagem perderia o contraste necessário para explicar por que um perfil foi preterido em favor de outro.

Duas decisões de persistência

Nada é apagado de verdade. Desenvolvedores e habilidades têm um campo ativo. Uma exclusão física quebraria o histórico de recomendações que já citam aquele registro.

Escores são BigDecimal, não double. Um softSkillsScore de 4.10 precisa voltar do banco como 4.10, não como 4.099999. Há um teste travando exatamente isso.

Enums e o dataset

Onde o domínio Java encosta na matriz de treinamento.

O modelo foi treinado sobre a Stack Overflow Developer Survey 2024, e as colunas daquela matriz têm nomes literais como Developer, back-end. Se esses nomes ficassem espalhados como texto solto pelo código, qualquer divergência de grafia produziria um vetor de atributos silenciosamente errado — e o modelo não reclamaria, apenas devolveria um escore ruim.

A solução foi guardar o rótulo dentro do próprio enum:

public enum PapelAtuacao {
    BACKEND  ("Developer, back-end",   "Backend"),
    FRONTEND ("Developer, front-end",  "Frontend"),
    FULLSTACK("Developer, full-stack", "FullStack"),
    MOBILE   ("Developer, mobile",     "Mobile"),
    QA       ("Developer, QA or test", "QA / Testes"),
    DEVOPS   ("DevOps specialist",     "DevOps");
    // chaveDataset ─┘                    └─ descricao (interface)
}

Um teste automatizado verifica essa correspondência. Se alguém renomear uma chave, o build quebra antes de o erro chegar ao motor de predição.

Todos são persistidos por nome (EnumType.STRING), nunca por índice. Se um nível de senioridade for inserido no meio da lista amanhã, os registros existentes continuam corretos.

Motor de predição

O modelo, o que ele recebe e como o backend chega nesses valores.

O modelo é um LightGBM escolhido pelo compare_models do PyCaret e otimizado com tune_model. Ele foi treinado sobre os 33.462 perfis da pesquisa cruzados com cenários de projeto simulados, e recebe 13 variáveis por candidato: sete do desenvolvedor, três do projeto e duas que só existem para o par desenvolvedor–projeto.

Nivel_Senioridade DevOps specialist Developer, QA or test Developer, back-end Developer, front-end Developer, full-stack Developer, mobile Soft_Skills_Score Proj_Criticidade Proj_Requisito_Backend Proj_Requisito_Frontend Aderencia_Tecnica Cobertura_Horas
do desenvolvedor do projeto relacional: calculada para cada par

VariávelOrigem no bancoCálculo
Nivel_Senioridade Desenvolvedor.senioridade Júnior = 1, Pleno = 2, Sênior = 3

Os cálculos ficam em MontadorVetorAtributos, isolado e testado sem banco, porque uma divergência em relação ao script de treinamento não gera erro nenhum: o modelo apenas pontua algo diferente do que aprendeu. As duas últimas variáveis são arredondadas em quatro casas, a mesma escala em que são gravadas.

O contrato com o serviço

O projeto vai uma vez; os candidatos vão em lote. O one-hot dos papéis é montado no Python, onde o treino aconteceu.

POST /predicoes
{
  "projeto": { "criticidade": 3, "requisitoBackend": true, "requisitoFrontend": false },
  "candidatos": [
    { "id": 1, "nivelSenioridade": 3, "papel": "Developer, back-end",
      "softSkillsScore": 4.0, "aderenciaTecnica": 0.75, "coberturaHoras": 0.9 }
  ]
}
→ { "algoritmo": "LGBMRegressor", "predicoes": [ { "id": 1, "score": 91.015 } ] }

O serviço recusa com 422 tudo que está fora do domínio de treino: senioridade 4, cobertura acima de 1, papel desconhecido, projeto sem nenhum requisito, lote vazio ou id repetido. Árvores de decisão não falham com esses valores, apenas os tratam como o extremo mais próximo, sem aviso. Se o .pkl carregado não tiver exatamente as 13 colunas esperadas, o serviço nem sobe.

O fluxo de uma recomendação

São três etapas, nesta ordem, para que a espera pelo motor não prenda uma conexão do banco durante até 15 segundos de timeout:

  1. Leitura, em transação somente leitura: projeto com papéis e stack, desenvolvedores ativos com competências e horas já alocadas em outros projetos. As variáveis são calculadas aqui.
  2. Motor, sem transação: MotorPredicaoClient envia o lote. Falha de conexão, timeout, recusa ou candidato sem escore viram 503.
  3. Gravação: ordena por escore, com empate desfeito pelo nome, compõe a equipe e grava a recomendação com as métricas e o ranking completo.

Duas armadilhas do ambiente Python. O pip install pycaret traz o LightGBM 4.7.0, que derruba o processo com access violation ao prever com este modelo; o requirements.txt fixa a 4.6.0. E o .pkl não é versionado: precisa ser copiado para api_motor_predicao/ antes de subir o serviço.

Composição e métricas

O escore avalia pessoas uma a uma. A equipe precisa de regras.

Como a equipe é formada

As regras rodam depois do ranqueamento, em ComposicaoEquipe, na ordem abaixo:

  1. Elegibilidade. Só entra quem tem livres todas as horas semanais exigidas, ou seja, coberturaHoras = 1. Um escore alto não compensa falta de tempo. Inelegíveis continuam no ranking com elegivel: false.
  2. Vagas por papel. Cada vaga declarada vai para o elegível de maior escore com exatamente aquele papel.
  3. Posições livres. O restante, até o tamanho da equipe, vai para os maiores escores ainda não escolhidos, de qualquer papel.

Sem elegíveis suficientes, a equipe sai parcial em vez de não haver resultado, e o campo observacaoRestricao explica o que faltou: integrantes, candidatos sem horas, vagas sem o papel exigido e tecnologias obrigatórias que ninguém da equipe domina.

As métricas de avaliação

Calculadas por CalculadoraMetricas e gravadas na recomendação. A calculadora não sabe como a equipe foi formada, e é por isso que serve também para a linha de base.

MétricaCálculoMelhor quando
coberturaPapeis Σ min(integrantes do papel, vagas do papel) ÷ vagas exigidas × 100 Maior
coberturaTecnologias Σ pesos das tecnologias dominadas por ao menos um integrante ÷ Σ pesos × 100 Maior
desvioPadraoSenioridade Desvio padrão populacional do nível 1–3 dos integrantes Menor: equipe nivelada
desvioPadraoScore Desvio padrão populacional dos escores dos integrantes —
scoreMedioEquipe Média dos escores dos integrantes Maior

O min da cobertura de papéis impede que três backends compensem a falta de um frontend. Sem papéis ou sem stack exigidos, a cobertura correspondente é 100.

Alocação e conflito entre projetos

A recomendação só sugere. Quem consome horas é a alocação, criada manualmente ou pela confirmação da equipe proposta, que aloca todos os selecionados de uma vez, no esquema tudo ou nada. A partir daí, essas horas são descontadas na coberturaHoras de qualquer outro projeto.

No teste de ponta a ponta com o modelo real, dois projetos disputavam os mesmos seis desenvolvedores. Antes de confirmar o projeto A, as duas equipes propostas tinham três pessoas em comum. Depois da confirmação, essas três passaram a inelegíveis no projeto B, que foi montado sem nenhuma sobreposição. Tentar alocar uma delas à mão devolve 422 com as horas livres que ela ainda tem.

Linha de base aleatória

Responde se a equipe proposta é melhor do que uma escolha sem critério. O endpoint GET /api/recomendacoes/{id}/linha-base sorteia equipes do mesmo tamanho apenas entre os elegíveis daquela recomendação, o mesmo grupo de onde o protótipo escolhe, mede cada uma com a mesma calculadora e devolve média e desvio padrão de cada métrica. A semente fixa torna o resultado reproduzível.

Exemplo · cenário de teste, 6 desenvolvedores fictícios, 100 sorteios

MétricaProtótipoAleatório (média ± desvio)
Cobertura de papéis (%)100,0081,50 ± 24,14
Cobertura de tecnologias (%)86,6780,80 ± 14,21
Desvio padrão da senioridade0,4710,622 ± 0,220
Escore médio da equipe80,6370,29 ± 6,01

Esses números validam o mecanismo, não o trabalho. Vieram de dados inventados para testar o fluxo. Os valores das tabelas de resultados precisam sair dos cenários de avaliação definidos no texto, rodados logo após cada recomendação, já que a linha de base usa requisitos e perfis atuais.

Regras de composição da equipe

Concluída

Onde as métricas do trabalho deixaram de ser texto e viraram código executável.

6

Interface conversacional

Concluída

Spring AI e Gemini, no papel duplo previsto na metodologia. Validada com o gemini-2.5-flash.

  • Na saída: POST /api/recomendacoes/{id}/justificativa, a partir do ranking, das métricas e das restrições gravadas; o texto fica na recomendação e regerar=true pede outro
  • Na entrada: extração de parâmetros a partir de texto livre (POST /api/recomendacoes/conversa)
  • System prompts versionados em resources/prompts
  • Conversa em turnos (POST /api/recomendacoes/conversa/turnos): o cliente envia o histórico, o backend pergunta o que falta e, completo, cria o projeto e a recomendação com origem CHAT
  • Sem chave configurada, os endpoints respondem 503 explicando o que falta; o resto da API segue funcionando

Decisões e trade-offs

Inclusive as que foram tomadas contra a recomendação inicial.

DecisãoAlternativaConsequência
Spring Boot 3.5.16 Boot 4.x Bate com o texto do TFG e garante o Spring AI na Fase 6
Aderência e cobertura calculadas no backend Enviar a stack inteira do projeto ao modelo Treze colunas em vez de dezenas; cada termo da fórmula vira uma variável rastreável
Disponibilidade como regra de elegibilidade Deixar só o peso no modelo Os cenários de escassez e conflito ficam determinísticos e explicáveis
Chamada ao motor fora da transação @Transactional no método inteiro Uma lentidão do motor não prende conexão do banco
Linha de base só entre elegíveis Sortear entre todos os ativos Comparação mais rigorosa: a única diferença passa a ser o critério de escolha
Senioridade com 3 níveis Manter ESPECIALISTA = 4 O modelo só viu 1–3; um quarto nível seria tratado como sênior sem aviso
ddl-auto: update Flyway versionado Mais rápido agora; o esquema não fica versionado. Flyway pode ser plugado depois sem refazer o domínio
Sem autenticação Spring Security + JWT Reduz o escopo do protótipo. Os três atores existem no caso de uso, mas não são impostos pelo backend
Exclusão lógica DELETE físico O histórico de recomendações permanece íntegro
Ranking completo gravado Só os selecionados Mais linhas no banco, em troca de transparência e contexto para o LLM

Sobre o ddl-auto e a ausência de autenticação. As duas foram escolhas conscientes de escopo, não esquecimentos. Vale ter a resposta pronta caso a banca pergunte: o esquema é derivado das entidades, e o controle de acesso está modelado no caso de uso mas não implementado neste protótipo.

Como rodar e testar

Não é preciso instalar Maven — o projeto traz o wrapper.

1 · Banco de dados

O perfil padrão é local, com PostgreSQL. As credenciais ficam em um único .env, lido tanto pelo Docker quanto pelo Spring:

cd backend
cp .env.example .env          # defina DB_PASSWORD
docker compose up -d          # PostgreSQL 17 em localhost:5433

A porta 5433 evita conflito com um PostgreSQL instalado na máquina. Para usar o instalado, ajuste DB_PORT=5432 no .env e crie o banco teamrec.

2 · Motor de predição

cd api_motor_predicao        # com motor_predicao_tcc.pkl nesta pasta
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m uvicorn app.main:app --port 8000

Só é necessário para gerar recomendações; o restante da API funciona sem ele.

3 · Backend

cd backend
./mvnw spring-boot:run                                   # perfil local
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev    # H2 em memória, sem Docker

Está no ar quando o log mostrar Started TeamrecApplication.

Consultas para começar:

-- A equipe proposta na última recomendação, com as variáveis usadas
SELECT d.NOME, m.POSICAO_RANKING, m.SCORE_AFINIDADE,
       m.ADERENCIA_TECNICA, m.COBERTURA_HORAS, m.SELECIONADO
FROM RECOMENDACAO_MEMBRO m
JOIN DESENVOLVEDOR d ON d.ID = m.DESENVOLVEDOR_ID
WHERE m.RECOMENDACAO_ID = (SELECT MAX(ID) FROM RECOMENDACAO)
ORDER BY m.POSICAO_RANKING;

-- Métricas e restrições de cada execução
SELECT ID, PROJETO_ID, COBERTURA_PAPEIS, COBERTURA_TECNOLOGIAS,
       DESVIO_PADRAO_SENIORIDADE, SCORE_MEDIO_EQUIPE, OBSERVACAO_RESTRICAO
FROM RECOMENDACAO ORDER BY ID;

-- Horas comprometidas por desenvolvedor
SELECT d.NOME, d.HORAS_DISPONIVEIS, SUM(a.HORAS_SEMANAIS) AS ALOCADAS
FROM ALOCACAO a JOIN DESENVOLVEDOR d ON d.ID = a.DESENVOLVEDOR_ID
WHERE a.ATIVA = TRUE
GROUP BY d.NOME, d.HORAS_DISPONIVEIS;

Configuração

Variáveis do .env: DB_NAME, DB_PORT, DB_USERNAME, DB_PASSWORD (ou DB_URL completa), PREDICTION_BASE_URL, GEMINI_API_KEY e APP_CORS_ORIGINS. Nenhum segredo é versionado.

Quando a porta 8080 ou 8000 aparecer ocupada

Normalmente é um processo órfão de uma execução anterior — o spring-boot:run executa a aplicação em um processo separado, que sobrevive ao encerramento do Maven. Para identificar e encerrar:

Get-Process -Id (Get-NetTCPConnection -LocalPort 8080 -State Listen).OwningProcess
Stop-Process -Id <PID> -Force
