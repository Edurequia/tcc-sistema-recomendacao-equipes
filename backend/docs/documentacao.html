O problema

Por que este backend existe.

Em ambientes de projeto de software, a composição de equipes costuma ser feita manualmente, com base na percepção individual do gestor e na disponibilidade imediata das pessoas. O resultado são times desnivelados — falta de competências essenciais, sobreposição de funções, sobrecarga dos profissionais mais experientes.

O sistema ataca isso em duas frentes que se complementam. Um motor preditivo calcula, para cada desenvolvedor, um escore de afinidade com o projeto. Um modelo de linguagem traduz esse número em uma justificativa legível, porque um escore sem explicação não sustenta uma decisão de alocação.

Este backend é a peça que amarra as duas. Ele não calcula o escore nem redige o texto: ele guarda o domínio, monta o que cada serviço precisa receber, aplica as regras de composição da equipe e devolve um resultado coerente.

O que o sistema precisa responder

  • Dado um projeto com papéis, stack e criticidade definidos, quem deve compor a equipe?
  • A equipe sugerida cobre todos os papéis e tecnologias exigidos?
  • O time está nivelado, ou é só um bloco de júniores em um projeto crítico?
  • Quando dois projetos disputam a mesma pessoa, quem fica com ela?
  • Por quê — em português, não em número.

Arquitetura

Quatro peças, dois ecossistemas, um orquestrador.

A arquitetura é de microsserviços por uma razão concreta: o motor de predição vive no ecossistema Python, onde estão as bibliotecas de aprendizado de máquina, enquanto a lógica de negócio e a persistência vivem no ecossistema Java. Em vez de forçar os dois no mesmo processo, cada um roda onde é forte e conversam por HTTP.

Quem faz o quê

As duas vias de entrada

O trabalho prevê uma abordagem híbrida, e os dois caminhos convergem para a mesma pipeline de recomendação:

  • Fluxo estruturado — o gestor preenche formulários; o React envia JSON; o backend processa.
  • Fluxo conversacional — o gestor descreve a necessidade em português; o Gemini converte o texto em parâmetros de busca; a partir daí o caminho é idêntico.

É por isso que a entidade Recomendacao guarda um campo origem: as duas vias produzem o mesmo tipo de resultado, mas saber por qual delas o gestor chegou é dado de pesquisa deste trabalho.

Sobre o Spring Boot 3 e não 4. O Spring Initializr já não gera projetos 3.x, e o padrão hoje é a linha 4. Mesmo assim o projeto ficou no 3.5.16 por dois motivos: é a versão declarada no texto do TFG, e o Spring AI 1.1.x — que fornece a integração com o Gemini — tem como alvo o Boot 3.5. Adotar o Boot 4 exigiria o Spring AI 2.x e criaria um risco de incompatibilidade justamente na Fase 6.

Sobre o acesso ao Gemini

O Spring AI oferece dois caminhos para os modelos do Google. O escolhido é spring-ai-starter-model-google-genai, que fala com a API do Gemini via chave de API — sem exigir conta na Google Cloud. A alternativa, vertex-ai-gemini, roteia pela Vertex AI e demanda projeto configurado no GCP, o que não se justifica em um protótipo acadêmico.

O caminho de uma requisição

  1. O controller recebe o JSON, que o Spring desserializa em um record de request. O @Valid reprova o que estiver fora das regras antes de qualquer código de negócio rodar.
  2. O controller chama o service e não faz mais nada — sem try/catch, sem consulta ao banco, sem lógica.
  3. O service abre a transação, usa os repositórios para carregar e gravar entidades, e aplica as regras.
  4. O mapper converte a entidade em um record de response.
  5. O controller devolve o record. A entidade JPA nunca chega ao JSON.

As quatro regras que sustentam isso

RegraO que ela evita
Entidade nunca vira JSON Vazar estrutura interna do banco na API e quebrar o React a cada refatoração
@Transactional só no service Transações abertas durante a serialização, prendendo conexão do pool
open-in-view: false Consultas disparadas silenciosamente na hora de gerar o JSON
Um repositório por agregado Alterar uma associativa por fora e deixar o objeto pai inconsistente

A terceira merece uma nota: com open-in-view ligado — que é o padrão do Spring Boot — a sessão do Hibernate fica aberta até a resposta ser escrita, e coleções preguiçosas são carregadas durante a serialização, uma consulta por item. Desligando, o carregamento passa a ser explícito no service, com JOIN FETCH.

Contrato de erros

Um formato só, para o React não tratar cada rota de um jeito.

Toda falha passa por um @RestControllerAdvice e sai no mesmo formato. Nenhum stacktrace chega ao cliente.

A separação entre 400 e 422 é deliberada. Pedir uma equipe de -3 pessoas é um erro de formato: 400. Pedir uma equipe de 8 pessoas quando existem 3 desenvolvedores disponíveis é uma requisição bem formada que o domínio recusa: 422. E o 503 existe para que a queda de um serviço de apoio não derrube o backend inteiro.

As regras que o cadastro de projeto impõe

Todas existem para impedir que uma especificação incoerente contamine as métricas calculadas na Fase 5.

RegraRespostaPor quê
Vagas por papel não excedem o tamanho da equipe 422 Somar mais tornaria a cobertura de papéis matematicamente inatingível
Somar menos é permitido 201 São posições sem papel fixo, preenchidas por quem tiver melhor escore
Cada papel declarado uma única vez 422 Duas quantidades para o mesmo papel são ambíguas

O campo vagasSemPapelFixo devolvido pela API é a diferença entre o tamanho da equipe e as vagas distribuídas. Maior que zero significa que parte do time fica em aberto — informação que a Fase 5 usará ao montar a composição.

Três decisões que aparecem no contrato

A normalização acontece no DTO, não no service. O Jackson constrói o record e só então o Bean Validation examina os campos. Aparar e converter para minúsculas dentro do compact constructor faz com que um e-mail colado com espaço em volta seja aceito — se a limpeza ficasse no service, o @Email já teria reprovado com 400.

A listagem não traz as competências. Carregá-las para cada linha da página dispararia uma consulta por desenvolvedor. Quem precisa da lista completa busca o perfil pelo identificador.

Duplicata é recusada, não resolvida em silêncio. Informar a mesma habilidade duas vezes, com proficiências diferentes, devolve 422 em vez de o backend escolher uma delas. Qualquer escolha automática gravaria algo diferente do que o cliente pretendia. Vale para desenvolvedores e para projetos.

O PUT substitui as competências, não acrescenta. É a semântica que o formulário do frontend espera: o que está na tela é exatamente o que fica gravado. Para mexer apenas nas horas existe o PATCH, que não corre o risco de apagar a lista sem querer.

Carga inicial do catálogo. Controlada pela propriedade app.seed.catalogo, ligada nos perfis dev e local. É idempotente: nada acontece se o catálogo já tiver registros. Sem ela não há como cadastrar competências que o motor de predição reconheça — um vínculo criado à mão, com grafia divergente, produziria um vetor de atributos silenciosamente incorreto.

As entidades

Desenvolvedor

O profissional candidato. É o “item” que o sistema recomenda.

nome · email único · senioridade · papelPrincipal · softSkillsScore 0–5 · horasDisponiveis · ativo

Catálogo centralizado de competências. Impede que “React”, “ReactJS” e “react” virem três entradas distintas.

DesenvolvedorHabilidade

Vínculo com atributo próprio — a proficiência —, por isso é entidade e não um N:N simples.

desenvolvedor · habilidade · proficiencia 1–5
Projeto

A demanda contra a qual os candidatos são avaliados.

nome · descricao · criticidade · status · tamanhoEquipe · horasSemanaisPorIntegrante · datas previstas
ProjetoPapelRequerido

Quantas vagas de cada papel. Base da métrica de cobertura de papéis.

projeto · papel · quantidade
ProjetoHabilidadeRequerida

A stack exigida. Base da métrica de cobertura de tecnologias.

projeto · habilidade · obrigatoria · peso 1–5
Recomendacao

Uma execução do motor. Cada rodada gera um registro novo; o histórico é dado de pesquisa.

projeto · origem · consultaOriginal · justificativaLlm · coberturaPapeis · coberturaTecnologias · desvioPadraoSenioridade · desvioPadraoScore · scoreMedioEquipe · observacaoRestricao
RecomendacaoMembro

Uma posição no ranking. O ranking inteiro é gravado, não só os escolhidos.

recomendacao · desenvolvedor · scoreAfinidade · papelSugerido · posicaoRanking · selecionado
Alocacao

O compromisso confirmado pelo gestor. Só ela consome horas.

desenvolvedor · projeto · papel · horasSemanais · dataInicio · dataFim · ativa

Por que Alocacao e RecomendacaoMembro são coisas diferentes. RecomendacaoMembro é uma sugestão do motor; Alocacao é um compromisso aceito. Sem essa separação, o cenário de avaliação “múltiplos projetos disputando os mesmos desenvolvedores” não teria como ser resolvido: não haveria como saber quantas horas de cada pessoa já estão de fato comprometidas.

Por que o ranking inteiro é gravado

Guardar só os selecionados economizaria linhas e custaria duas coisas. O gestor perderia a informação de quem ficou de fora e por qual margem — que é exatamente o que ele precisa para contestar a sugestão. E o modelo de linguagem perderia o contraste necessário para explicar por que um perfil foi preterido em favor de outro.

Duas decisões de persistência

Nada é apagado de verdade. Desenvolvedores e habilidades têm um campo ativo. Uma exclusão física quebraria o histórico de recomendações que já citam aquele registro.

Escores são BigDecimal, não double. Um softSkillsScore de 4.10 precisa voltar do banco como 4.10, não como 4.099999. Há um teste travando exatamente isso.

Enums e o dataset

Onde o domínio Java encosta na matriz de treinamento.

O modelo foi treinado sobre a Stack Overflow Developer Survey 2024, e as colunas daquela matriz têm nomes literais como Developer, back-end. Se esses nomes ficassem espalhados como texto solto pelo código, qualquer divergência de grafia produziria um vetor de atributos silenciosamente errado — e o modelo não reclamaria, apenas devolveria um escore ruim.

A solução foi guardar o rótulo dentro do próprio enum:

public enum PapelAtuacao {
    BACKEND  ("Developer, back-end",   "Backend"),
    FRONTEND ("Developer, front-end",  "Frontend"),
    FULLSTACK("Developer, full-stack", "FullStack"),
    MOBILE   ("Developer, mobile",     "Mobile"),
    QA       ("Developer, QA or test", "QA / Testes"),
    DEVOPS   ("DevOps specialist",     "DevOps");
    // chaveDataset ─┘                    └─ descricao (interface)
}

Um teste automatizado verifica essa correspondência. Se alguém renomear uma chave, o build quebra antes de o erro chegar ao motor de predição.

Todos são persistidos por nome (EnumType.STRING), nunca por índice. Se um nível de senioridade for inserido no meio da lista amanhã, os registros existentes continuam corretos.

A última linha é a mais importante. A disponibilidade enviada ao modelo não é o campo bruto do cadastro: é o campo menos as horas já comprometidas em projetos ativos. É isso que faz uma pessoa já lotada em dois projetos cair naturalmente no ranking, sem nenhuma regra especial.

Contrato ainda não fechado. O formato exato de requisição e resposta do serviço FastAPI — nomes dos campos JSON, se aceita um lote de candidatos ou um por vez, se recebe também os atributos do projeto — depende do arquivo do modelo, que ainda não está disponível. A Fase 4 começa por definir esse contrato.

Decisões e trade-offs

Inclusive as que foram tomadas contra a recomendação inicial.

DecisãoAlternativaConsequência
Spring Boot 3.5.16 Boot 4.x Bate com o texto do TFG e garante o Spring AI na Fase 6
ddl-auto: update Flyway versionado Mais rápido agora; o esquema não fica versionado. Flyway pode ser plugado depois sem refazer o domínio
Sem autenticação Spring Security + JWT Reduz o escopo do protótipo. Os três atores existem no caso de uso, mas não são impostos pelo backend
Exclusão lógica DELETE físico O histórico de recomendações permanece íntegro
Ranking completo gravado Só os selecionados Mais linhas no banco, em troca de transparência e contexto para o LLM
H2 no perfil dev Só PostgreSQL Roda sem instalar nada; exige conferir o esquema no Postgres antes da entrega

Sobre o ddl-auto e a ausência de autenticação. As duas foram escolhas conscientes de escopo, não esquecimentos. Vale ter a resposta pronta caso a banca pergunte: o esquema é derivado das entidades, e o controle de acesso está modelado no caso de uso mas não implementado neste protótipo.

Como rodar e testar

Não é preciso instalar Maven — o projeto traz o wrapper.

Subir a aplicação

Pelo IntelliJ, basta executar a classe TeamrecApplication: o perfil dev é o padrão e não exige nenhuma configuração. Pelo terminal:

# perfil dev — H2 em memória, zero instalação
cd backend
./mvnw spring-boot:run

O console do H2 abre em localhost:8080/h2-console. O campo JDBC URL vem preenchido com um valor genérico e precisa ser substituído — é o erro mais comum ao conectar:

O banco vive em memória. Tudo é descartado quando a aplicação para, e o catálogo de 38 competências é recriado a cada inicialização. É intencional no perfil dev: cada execução parte de um estado limpo e reprodutível.

Consultas para começar:

-- As 30 tecnologias e a coluna correspondente na matriz de treinamento
SELECT NOME, CHAVE_DATASET, CATEGORIA FROM HABILIDADE
WHERE CHAVE_DATASET IS NOT NULL ORDER BY NOME;

-- Desenvolvedores com suas competências e proficiências
SELECT d.NOME, d.SENIORIDADE, d.PAPEL_PRINCIPAL,
       h.NOME AS COMPETENCIA, dh.PROFICIENCIA
FROM DESENVOLVEDOR d
JOIN DESENVOLVEDOR_HABILIDADE dh ON dh.DESENVOLVEDOR_ID = d.ID
JOIN HABILIDADE h ON h.ID = dh.HABILIDADE_ID
ORDER BY d.NOME;

-- Papéis exigidos por projeto
SELECT p.NOME, pp.PAPEL, pp.QUANTIDADE
FROM PROJETO p
JOIN PROJETO_PAPEL_REQUERIDO pp ON pp.PROJETO_ID = p.ID;

Exercitar a API

Há dois caminhos, com propósitos diferentes.

Swagger UI, em localhost:8080/swagger-ui.html, lista os 19 endpoints com seus campos e um botão para executar direto do navegador. É o melhor recurso para explorar o contrato.

O arquivo backend/api.http traz um roteiro de 37 requisições encadeadas, executáveis uma a uma pelo cliente HTTP do IntelliJ. Ele captura os identificadores automaticamente — os das competências, o do desenvolvedor criado, o do projeto —, de modo que nenhum valor precisa ser copiado manualmente entre requisições.

Configuração

Copie .env.example para .env e preencha. Nenhum segredo é versionado: DB_PASSWORD, GEMINI_API_KEY, PREDICTION_BASE_URL e APP_CORS_ORIGINS vêm todos do ambiente.

Quando a porta 8080 aparecer ocupada

Normalmente é um processo Java órfão de uma execução anterior — o spring-boot:run executa a aplicação em um processo separado, que sobrevive ao encerramento do Maven. Para identificar e encerrar:

Get-Process -Id (Get-NetTCPConnection -LocalPort 8080 -State Listen).OwningProcess
Stop-Process -Id <PID> -Force
